## 一、AI 对话逻辑

**对话流程**：用户输入 → client 发送 `POST /v1/chat`（SSE）→ 后端在该会话的 LangGraph 陪伴主图中执行 → 感知门控路由到陪伴 agent（含 ReAct 工具循环）或游戏占位子图 → agent 节点逐 token 回流 → 事件流回传（`turn.start` / `state` / `text.delta` / `emotion` / `tool.*` / `turn.end`）→ 聊天框增量显示、表情播放、语音播报。

- **单引擎**：`backend/core/facade.py` 固定构造 LangGraph 陪伴主图（`CompanionGraphAgent`），旧 `ChatAgent` 与 `AGENT_ENGINE` 回滚开关已归档到 `archive/legacy_multi_mode/`
- **主图结构**：`START → perception_gate`；`route == "game"` 进入 `game_subgraph`（当前为“游戏开发中”占位回应），否则进入 `agent ⇄ tools` 循环后结束。工具节点 `ToolNode(..., handle_tool_errors=True)` 把工具异常转成 `ToolMessage`，图不中断
- **感知门控**：优先使用 FakeJev 对“是否在请求游戏”做置信度判断（阈值 `> 0.7`），依赖不可用时回落关键词规则；用户消息的时间前缀在路由前剥离
- **工具调用**：天气 / 搜索由主图 `backend/agent/graph/tooling.py` 的 `BASE_TOOL_MAP` 自持装配，可选合并 MCP 工具，每轮 `bind_tools` 后由模型自主决定；时间能力已迁至 `utils/time_utils.py`，不再作为工具暴露给模型
- **MCP（可选）**：读取 `MCP_CONFIG_PATH`（默认 `config/mcp_servers.json`），用 `MultiServerMCPClient.get_tools()` 加载并加服务名前缀；未配置、配置损坏、连接异常或 10s 超时均只告警并降级为空列表，不影响启动。真实配置不入库，模板见 `config/mcp_servers.example.json`
- **时间注入**：用户消息写入图状态时加 `[YYYY-MM-DD HH:MM] ` 前缀，AI 最终回复追加 ` [YYYY-MM-DD HH:MM]` 后缀；流式 token 与 UI 展示的都是剥离时间后的干净正文，模型若自行复述时间戳也会被 `strip_time_markers()` 清除；提示词路径统一由 `config/prompts_config.yml` 提供
- **情绪契约**：模型输出 `[emotion:xxx]` 前缀 + 正文，节点解析后剥离标签并把情绪写入 `additional_kwargs["emotion"]`；合法标签以 `backend/agent/expression_driver.VALID_EMOTIONS` 的 10 种为准（happy / sad / angry / surprised / neutral / shy / worried / excited / thinking / relaxed）
- **对话记忆**：主图编译挂 `MemorySaver`，以 `thread_id = session_id` 隔离多轮上下文；每轮结束把完整消息镜像到 `chat_history/<session>.json`（裁剪 30 条非 system 消息），进程重启时首次注入恢复
- **模型工厂**：连接参数（`API_KEY` / `BASE_URL` / `MODEL`）从 `.env` 读取，生产 langchain `ChatOpenAI`，支持 DeepSeek、通义兼容端、本地 vLLM 等任意 OpenAI 协议模型
- **前后端边界**：UI 只依赖 `client/transport` 的 `send / interrupt / close` 与两个信号；`emotion` 事件经 `client/emotion_map.py` 转成动作组，再由唯一跨线程入口 `Live2DWidget.request_play_motion` 投递到主线程执行

**单模式说明**：当前固定为情感陪伴单模式，`ChatRequest` 不再携带 `mode`，协议 `turn.start.mode` 字段保留并固定为 `"emotion"`（避免破坏客户端解析）。旧多模式配置（`emotion` / `office` 注册表）已归档，不再参与运行；后续扩展走游戏子图与工具层，不恢复模式路由。

## 二、TTS 语音合成方案

桌宠播报语音由 `client/voice/tts.py` 负责，通过 `.env` 的 `TTS_MODE` 切换运行模式：

- **demo（演示模式，默认）**：优先 qwen3-tts（阿里云百炼，多语言混说 + 自定义音色），失败时 edge-tts 兜底
- **dev（开发模式）**：仅使用 edge-tts（免费、零配置，不依赖 API Key）

### 方案对比

| 方案 | 多语言混说 | 部署/配置 | 音色 | 成本 | 说明 |
| --- | --- | --- | --- | --- | --- |
| **edge-tts** | 弱 | 云端、零配置 | 固定 | 免费 | 免费但固定音色，用作兜底方案 |
| **GPT-SoVITS** | 否 | 本地、部署困难 | 自训练 | 免费 | 吃电脑配置，需先自训练模型，无法多语言混说，本地部署困难 |
| **genie-tts** | 否 | 本地 CPU 可跑 | 演示/自训练 | 免费 | 解决了 GPT-SoVITS 的配置和部署问题，CPU 能跑，有演示模型，但依旧无法多语言混说（已弃用） |
| **qwen3-tts** | 是 | 云端、需 API Key | 固定 + 声音设计 | 付费 | 有固定音色且能便捷生成独特音色（灵活性偏低，不能克隆指定角色音色；qwen3-tts-vc 模型支持声音复刻），支持多语言混说 |
| **moss-tts-nano** | 是 | 本地、配置要求低 | 固定 + 自训练 | 免费 | 免费，配置要求低，支持多语言混说，有固定音色和可训练自训练音色，但自训练音色官方缺少资料，可未来考虑 |
| **fish-speech** | 是 | 本地吃配置 / 云端可克隆 | 可克隆 | 免费/付费 | 满足大部分需求，但吃本地配置；云端方案能克隆音色，可尝试云端方案 |
| **meloTTS** | 弱 | 本地、低配置可跑 | 少量固定 | 免费 | 少量固定音色，无法克隆或训练，但可低配置本地推理，可未来成为兜底方案 |

### 当前状况与未来方向

- **当前**：暂时使用 edge-tts 和 qwen3-tts 切换进行桌宠 TTS 服务
- **未来主力**：云端 fish-speech（可克隆音色）和 moss-tts-nano（优先考虑 fish-speech）
- **本地部署**：电脑配置问题解决后，可选本地 fish-speech
- **兜底演进**：edge-tts 可替换为 meloTTS

> 注：edge-tts 依赖的上游接口做过握手版本变更（旧版本会返回 403），已通过升级到 `edge-tts>=7.3.1` 解决，详见开发记录。

## 三、Live2D 表情动画系统

情感标签 → 动作组的映射定义在 `client/emotion_map.py` 的 `EMOTION_MOTION_MAP`，当前接入了 HiYori 模型自带的 6 组动作：

| 情感标签 | 动作组 | 含义 |
| --- | --- | --- |
| `thinking` | `Idle` | 了解并思考 |
| `relaxed` | `Flick` | 悠闲 / 摇头晃脑 |
| `shy` | `FlickDown` | 害羞 |
| `surprised` | `Tap` | 惊讶 |
| `angry` | `Tap@Body` | 生气 |
| `sad` | `Flick@Body` | 难过 |
| `happy` / `neutral` / `worried` / `excited` | — | 暂无对应动作，保持常态（自动呼吸 / 眨眼） |

### 鼠标跟随

`Live2DWidget` 每帧（120fps）读取全局光标，经 `mapFromGlobal` 转为部件坐标后，由 `client/live2d_behavior.py` 的纯函数处理：

1. `normalize_cursor`：映射为 `[-1, 1]` 并限幅（窗口外也会朝边角看）；
2. `smooth_toward`：按系数 `CURSOR_SMOOTH_FACTOR = 0.25` 做指数平滑（约 90ms 收敛，避免抖动）；
3. `denormalize_cursor`：还原为与 `model.Resize` 同尺度的像素坐标，调用 `model.Drag`。

表情动作播放与回归过渡期间暂停 `Drag`，结束后从上次平滑值继续，避免与动作角度互相覆盖。

### 动作状态机与优先级

状态由 `Live2DWidget._motion_state` 管理，纯函数定义在 `client/live2d_behavior.py`：

| 状态 | 触发 | 迁移 |
| --- | --- | --- |
| `idle` | 常态待机 | 空闲 8~15s 后播放随机动作 → `random_playing`；收到表情 → `emotion_playing` |
| `random_playing` | `StartRandomMotion(group, NORMAL)` | 动作结束 → `idle` 并重新计时 |
| `emotion_playing` | `StartMotion(group, FORCE)`，取消随机计时 | 动作结束 → `emotion_returning` |
| `emotion_returning` | smoothstep 平滑回常态（1.5s） | 过渡完成 → `idle`，恢复跟随与随机调度 |

随机动作组从 `GetMotionGroups()` 的实际组中随机选择（避开上一次），表情动作始终以 `FORCE` 优先级覆盖随机动作；打断（`reset_emotion`）直接回到 `idle`。

### 平滑回常态机制

`client/ui/live2d_widget.py` 的 `Live2DWidget` 在每次表情动作播放结束后，会用 **smoothstep 缓动**在 1.5 秒内把全部参数从动作末值平滑插值回 `default`（常态），过渡完成再恢复自动眨眼 / 呼吸。避免动作一结束就跳变回中性参数导致不自然。

### 跨线程安全

`emotion` 事件在传输线程（`SseWorker`）被解析，`drive_expression` 通过 `Live2DWidget.request_play_motion` 信号把动作播放请求转发到主线程执行，避免子线程直接操作 OpenGL 导致崩溃；打断时调用 `reset_emotion()` 立即停止动作并恢复常态。

## 四、Live2D 表情动画调试台

`scripts/expression_tester.py` 是一个独立运行的调试工具，用于在接入主程序前先在 HiYori 模型上探索、组合并保存自定义神态 / 动作，再迁入主程序。

```bash
uv run python scripts/expression_tester.py
```

主要功能：

- **实时调参**：面部表情（脸朝向 / 眼睛 / 眉毛 / 嘴形 / 脸红）与身体肢体（左右臂 / 身体三轴）滑条，拖动立即生效，范围从模型真实 min/max 读取
- **一键肢体姿态**：双手举起 / 单手举起 / 身体倾斜 / 歪头卖萌 / 站姿归位等预设按钮，可与面部表情叠加
- **神态预设保存**：把当前表情 + 肢体组合保存为命名预设，存入 `expression_presets.json`（追加保存，重启不丢）
- **平滑过渡**：从当前姿态 smoothstep 过渡到指定预设，可调时长
- **动画序列**：把多个预设按顺序串联成动画，支持循环播放，存入 `expression_animations.json`
- **Dump 全部参数**：一键打印所有参数的 id / min / max / default / 当前值，方便了解模型能力边界

> 调试台产出的预设 / 动画是后续扩展自定义神态（不依赖模型自带动作）的原料，可由主程序按需加载。

## 五、性能评测

`evals/` 负责**行为正确性回归**（确定性 21 条 + live 冒烟 3 条，默认无网络、无 API Key），`bench/` 负责**性能与真实模型联通性**（固定 20 条 prompt：闲聊 / 时间 / 天气 / 搜索 / 情绪），逐条请求 `POST /v1/chat`，统计首事件延迟、整轮总延迟、工具调用与错误。两者分工详见 [评测说明](../evals/README.md)。

```
uv run python bench/run_bench.py --limit 3   # 先验证连通性（会真实调用大模型）
uv run python bench/run_bench.py             # 全量 20 条，自动拉起/回收后端
```

输出 `bench/result.csv`（每条一行）与控制台 P50/P95。当前本机基线（DeepSeek，20 条，独立 `bench` 会话）：

| 指标 | P50 | P95 |
| --- | --- | --- |
| 首事件延迟（请求发出 → 第一个 SSE 帧） | 3.3 ms | 5.0 ms |
| 整轮总延迟（请求发出 → `turn.end`） | 1.74 s | 5.29 s |

工具调用率 45%（9/20 触发工具），错误率 0%。首轮约 5.3s 属于 Agent 冷启动，非链路开销。

## 六、项目期望与规划

哈达莉的长期目标是做一个「伴随在桌面的、能陪伴也能干活的多功能 AI 助手」。当前以情感陪伴为主体：办公/编程不再是独立模式，而是主图在 ReAct 循环中按需调用的工具集；游戏互动作为独立子图横向扩展。后续沿「分层记忆 + 上下文工程 + 工具治理 + 评估体系」纵向深化，先跑通纵向切片再横向扩展。

> **口径说明**：本节按修订版架构设计（陪伴主图 ReAct + 游戏子图 + 工具层）描述，评估重心为「人格一致性 + 记忆可靠性 + 切换自然度」。旧版 Root-Subgraph 主子图 / 多模式路由方案已归档到 `archive/legacy_multi_mode/`，不再作为后续开发依据。

### 6.1 顶层拓扑：陪伴主图 + 游戏子图 + 工具层

办公/编程不再是独立模式，而是 Agent 主体在 ReAct 循环中可调用的工具集；陪伴对话始终是主体，游戏互动是独立分支。主图**不预设任何「模式」概念**，任务完成后自然回到陪伴语境。

| 组成 | 职责 | 当前实现 |
| --- | --- | --- |
| 陪伴主图 | 基于 ReAct（reason → tool_executor → respond）承载情感陪伴主循环；判断是否需要调用工具、进入游戏子图或直接情感回应 | `perception_gate → agent ⇄ tools`；reason 与 respond 目前合并在 `agent` 节点 |
| 游戏子图 | 有状态的多轮互动（棋盘、轮次、胜负判定），独立状态机与命名空间；结束后把「本局结果 / 关键落子」摘要写回主图状态 | 真 `StateGraph`，当前只有 `game_notice` 占位节点 |
| 工具层 | MCP 服务 + 自制轻量工具，作为 `tool_executor` 的能力池；按意图动态挂载，不全部常驻上下文 | 天气 / 搜索自制工具 + 可选 MCP；`OFFICE_TOOLS` 为空组预留 |

- **隔离要求**：工具调用产生的结构化上下文属于「任务级临时作用域」，不得污染人格设定与情感记忆；游戏状态与陪伴对话使用独立 `thread_id` / checkpointer 命名空间。
- **演进原则**：先纵向跑通陪伴主体，再横向扩展游戏与工具；新增能力不引入新的「模式路由」。

### 6.2 分层记忆架构

当前实现是 `MemorySaver` 热状态 + 单一 JSON 滑动窗口镜像（`chat_history/default.json`，最近 30 条），规划升级为四层记忆：

| 层级 | 定位 | 隔离方式 | 内容 | 当前状态 |
| --- | --- | --- | --- | --- |
| L3 会话热缓存 | 短期记忆 | 按 `thread_id`（= `session_id`）物理隔离 | 当前会话最近 N 轮对话 + 图状态快照 | 已实现（MemorySaver + JSON 镜像） |
| L2 结构化事实库 | 长期记忆 | 按 `namespace` 逻辑隔离 | 全局用户画像（称呼、沟通偏好、重要日期）、关系状态（互动摘要、亲密度）、工具任务偏好；异步提炼、新事实覆盖旧事实（遗忘感知） | 未实现 |
| L1 会话摘要 | 长对话连续性 | 按会话 | 按需压缩历史，作为关系状态演进的输入 | 未实现 |
| L0 向量库 | 深度情感回查（未来） | 全局共享 | Chroma / LanceDB 存全量对话，用于「上次聊到那件事后来怎么样了」 | 未实现 |

#### 6.2.1 工具上下文的作用域隔离

- 工具执行产生的结构化上下文**不写入陪伴记忆层**，仅存在于任务生命周期内；任务结束即丢弃或摘要归档。
- 若工具任务产生了对用户有价值的事实（如「用户项目用 LangGraph」），由事实提取节点**提炼为 L2 事实**后写入，而不是把原始工具日志塞进记忆。
- 现状：`runner._clean_history()` 在恢复与写镜像前已剥离 `ToolMessage` 与带 `tool_calls` 的 `AIMessage`，保证了「不污染」，但属于**丢弃**；后续应升级为「事实提炼后归档」。

### 6.3 上下文工程

在有限 Token 预算内兼顾推理质量与首 Token 延迟（TTFT），四项机制：

| 机制 | 设计 | 当前状态 |
| --- | --- | --- |
| 缓存边界划分 | Prompt 最前端固定放置人格设定 + 全局用户画像（高 KV-Cache 命中）；中段为关系状态摘要；后缀为最近对话与工具检索结果 | 部分：系统提示词每轮临时拼在最前，但未做缓存边界管理 |
| 预算动态分配 | 对话历史占 50–60%；人格与画像底座固定小比例且不可裁剪；工具结果按需注入并设上限（截断 / 摘要后再注入） | 未实现 |
| 工具结果标签化 | 工具返回内容强制附带 `[Tool: file_read]` 等标签，帮助模型区分「陪伴语境」与「工具事实」 | 未实现 |
| 人格守护 | Token 超限时优先压缩对话历史与工具结果，**人格设定与关系状态摘要永不裁剪** | 未实现（当前仅 30 条硬裁剪，不区分内容优先级） |

### 6.4 工具执行与安全（MCP + HITL）

工具层需要从「能调用」升级到「可控」：

- **MCP 接入**：`tool_executor` 作为 MCP 客户端按需发现与调用；已实现逐服务隔离加载、超时降级、async→sync 包装与工具名前缀，未配置时自动降级为空列表。
- **工具错误自愈**：工具异常不中断陪伴主循环，结构化错误回传 reason 节点，允许模型反思并重试或向用户自然说明。现状为 `ToolNode(handle_tool_errors=True)` 把异常转成 `ToolMessage`，由模型自行决定，尚无显式重试上限。
- **人在回路（HITL）**：针对删除文件、执行 Shell 等敏感 / 不可逆操作，在工具执行前用 `interrupt()` 挂起，用户「批准 / 修改 / 拒绝」后由 `Command(resume=...)` 从断点恢复。**未实现**；现有 `/v1/interrupt` 只是客户端 Esc 取消 SSE 流，与图内审批无关。
- **人格一致性**：工具调用前后的回复保持陪伴语调，避免「秒变工具人」的割裂感。

### 6.5 评估与可观测性

评估重心从「模式隔离」转向**陪伴质量 + 工具协同可靠性**，构建私有回归集：

| 类别 | 指标 |
| --- | --- |
| 北极星 | 人格一致性 / 漂移率；记忆可靠性（FAMA，偏好变更后弃用过时记忆、关键情感事件可召回）；工具-陪伴切换自然度 |
| 陪伴 | 人格漂移、情绪稳定性、共情质量、主动关心恰当性 |
| 游戏子图 | 状态机正确性（胜负判定、轮次）、跨轮次恢复稳定性 |
| 工具层 | 工具选择准确率、参数正确率、结果利用与错误恢复（工具四层评估） |

- **可观测性**：全链路接入 LangSmith，重点追踪 ReAct 循环中的工具调用链、游戏子图状态流转、记忆读写路径。现状仅本地 `logs/turns.jsonl`（`TurnTracer`）。
- **评测现状**：`evals/` 对应评测体系**阶段一（回归安全网）**，21 条确定性用例（M1 工具 / M2 路由 / M3 时间 / M4 容错 / M5 流式契约 / M6 记忆恢复）+ 3 条 live 冒烟；`evals/judges/`、`evals/probes/` 为阶段二占位；`bench/` 用 20 条固定 prompt 统计接口级延迟、工具调用率与错误率。指标编号与评测体系三阶段路线的对照见 `evals/README.md`。

### 6.6 更丰富的表情动画

当前已接入 HiYori 自带的 6 组动作。后续通过 `scripts/expression_tester.py` 探索参数组合，为更多情感标签设计自定义神态（不依赖模型自带动作），让哈达莉更生动；未来换用绑定更完整的模型后，动作空间会进一步打开（HiYori 无独立手脚绑定，大幅动作能力有限）。

### 6.7 屏幕识别与主动搭话

让哈达莉从「被动应答」走向「主动陪伴」，更贴合「桌面情感陪伴」的定位：

- **屏幕感知**：识别当前前台应用 / 窗口标题 / 工作状态，判断用户是否在忙
- **主动搭话**：基于时间（久坐提醒、深夜问候）、状态（长时间无操作、应用切换）和记忆（之前聊过的话题）主动发起对话
- **节奏控制**：避免打扰，尊重专注状态，搭话频率与时机可配
- **阶段归属**：属于阶段二「主动关心触发」，需以 L2 关系状态与用户画像作为触发依据，因此排在记忆系统之后

### 6.8 阶段演进与当前进度

修订版架构坚持「先纵向切片跑通，再横向扩展」：

| 阶段 | 目标 | 状态 |
| --- | --- | --- |
| 阶段一（MVP） | 陪伴主图 ReAct + 分层记忆（Checkpointer + Store）+ 1~2 个 MCP 工具 + 五子棋子图 + 错误处理 | **进行中**：主图 / Checkpointer / 错误处理 / 评测回归网已完成；Store 层、真实游戏子图待补 |

**本轮开发顺序调整**（优先 agent 核心技术）：先补阶段一缺失的 Store 层与上下文工程，再做记忆与人格增强、工具治理；**游戏子图暂缓**，其占位节点与 M2「倾诉中提游戏」路由反例作为评测资产保留，待核心能力就绪后再作为「子图隔离复用性」验证场启动。评测体系按三阶段路线同步迭代：阶段一（回归安全网，当前）→ 阶段二（LLM-as-Judge / 记忆可靠性探针 / 打断恢复）→ 阶段三（LangSmith datasets / CI 门控 / trace 回流）。
